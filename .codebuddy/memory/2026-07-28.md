## 修复 PermissionContextModeTest 测试失败（2个）

**根因分析**：

1. **Controller `@PreAuthorize` 权限表达式过于宽泛**：DELETE `/api/order/{id}` 使用 `@PreAuthorize("@permissionService.hasPermission('order:*')")`，`order:*` 会匹配用户已有的任何 order 权限（如 `order:create`），导致本应拒绝的请求被放行。

2. **测试间 UserContext 缓存污染**：`InMemoryUserContextCache` 使用 `static ConcurrentHashMap` 按 userId 缓存。所有测试用户（admin/user/guest）共享 `userId=1`。admin 测试先运行后缓存了 `*:*` 权限的 UserContext，后续 user/guest 测试命中缓存拿到 admin 的权限。

**修复**：

- **`PermissionTestController.java`**：DELETE 端点 `@PreAuthorize` 从 `order:*` 改为 `order:delete`（更精确的权限控制）
- **`PermissionContextModeTest.java`**：
  - 添加 `@BeforeEach setUp()` 清理 `UserContext.remove()` 和 `userContextCache.remove("1")`
  - 注入 `IUserContextCache` 用于缓存清理

**结果**：全部 12 个测试通过，框架代码未修改。

## 修复 ContextEndpointTest 测试失败（2个）

**根因**：`EndpointAvailabilityTests.testLoginEndpointAvailable` 调用 `login?userId=test` 设置了 UserContext（ThreadLocal），MockMvc 同线程运行导致 `CurrentUserTests` 拿到的不是 "No user logged in"。

**修复**：在 `ContextEndpointTest` 顶层类添加 `@BeforeEach setUp()` 调用 `UserContext.remove()`。

**结果**：全部 28 个测试通过，框架代码未修改。

## 修复 CoreEndpointTest 测试失败（4个）

**根因**：`UserContext` 是 ThreadLocal，`core-sample` 不依赖 `context-starter`，没有 `UserContextFilter` 来自动清除上下文。测试假设请求间上下文自动隔离，但实际在同一线程内上下文会残留。

**修复**：

- `CoreEndpointTest` 顶层添加 `@BeforeEach setUp()` 调用 `UserContext.remove()`（修复跨嵌套类污染，2个）
- `UserContextIsolationTests` 中 2 个测试：在 `set-user` 后显式调用 `/api/core/clear` 模拟请求间上下文清除（修复同方法内残留，2个）

**结果**：全部 22 个测试通过，框架代码未修改。

## 修复 GitHub Actions `test.yml` 构建失败

**根因**：`test.yml` 的 `Build and install dependencies` 步骤直接在 `./structure-security-samples` 目录执行 `mvn clean install -Dmaven.test.skip=true -q`。samples 依赖的 `structure-security-jwt-starter` 等模块版本为 `1.1.5-SNAPSHOT`，仅在本地项目中存在，远端仓库找不到，导致 `DependencyResolutionException`。

本地打包没问题是因为通常会先 build 主项目（structure-security-dependencies）再 build samples。

**修复**：在 `test.yml` 中新增 `Build and install main project` 步骤，先从 `structure-security-dependencies` 构建并 install 主项目（排除 samples），再构建 samples：

```yaml
- name: Build and install main project
  run: |
    mvn clean install -Dmaven.test.skip=true -q -pl '!../structure-security-samples'
  working-directory: ./structure-security-dependencies
```

**结果**：CI 能先在本地仓库安装主项目 artifact，samples 构建时可正常解析依赖。

## 修复示例工程被发布到 Maven Central 的问题

**根因**：`structure-security-samples/pom.xml` 中已设置 `<maven.deploy.skip>true</maven.deploy.skip>`，但 `release.yml` 激活的 release profile 会从父 POM（structure-dependencies）注入 `org.sonatype.central:central-publishing-maven-plugin`。该插件不遵守 `maven.deploy.skip`，在 deploy 阶段执行 `injected-central-publishing` 目标，导致示例工程被上传到 Maven Central 并因缺少 project name 等信息失败。

**尝试过的错误方案**：

1. 直接从 `structure-security-dependencies/pom.xml` 的 `<modules>` 中移除 samples —— 用户要求默认构建必须包含 samples，被拒绝。
2. 在 `structure-security-dependencies/pom.xml` 中定义 `release` profile，复写 `<modules>` 排除 samples —— Maven profile 的 `<modules>` 是**追加**而非替换，不生效。
3. 使用 `activeByDefault` 的 `samples` profile 默认包含 samples，期望 `-P release` 时自动失效 —— 实际未能正确排除 samples。

**正确修复**：

- `structure-security-dependencies/pom.xml`：默认 `<modules>` 保留 `structure-security-samples`。
- `structure-security-samples/pom.xml`：在 `<build><plugins>` 中覆盖父 POM 注入的 `central-publishing-maven-plugin`，将 `injected-central-publishing` 执行绑定到 `<phase>none</phase>`，彻底禁用该插件：

```xml
<plugin>
    <groupId>org.sonatype.central</groupId>
    <artifactId>central-publishing-maven-plugin</artifactId>
    <executions>
        <execution>
            <id>injected-central-publishing</id>
            <phase>none</phase>
        </execution>
    </executions>
</plugin>
```

- `release.yml`：保持 `mvn clean deploy -P release ...`，无需 `-pl '!...'` 排除。

**结果**：`mvn help:effective-pom` 验证示例工程的 `injected-central-publishing` 执行 phase 为 `none`，发布时 central-publishing 插件不会执行，示例工程不会被推送到 Maven Central，同时默认 CI/test 构建仍包含 samples。
